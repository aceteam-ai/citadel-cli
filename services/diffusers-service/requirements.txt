# History of the Wan2.1 floor (citadel #958); the current pin is further down.
# 0.33.1, not 0.31.0: WanPipeline/AutoencoderKLWan (citadel #958, Wan2.1
# text-to-video) were not exported yet at 0.31.0 -- verified directly against
# the tagged source (diffusers/__init__.py has no "Wan*" symbol at v0.32.0,
# both appear at v0.33.0). 0.33.1 also raises this package's OWN
# huggingface-hub floor to >=0.27.0 (see below) and transformers floor to
# >=4.41.2 / safetensors to >=0.3.1 / accelerate to >=0.31.0 -- all already
# comfortably satisfied by the pins below, so this bump is otherwise
# backward-compatible with the existing sdxl-turbo image path.
# Stack bumped for citadel-cli#1335 (per-request model selection), from
# diffusers 0.33.1 / transformers 4.46.3 / accelerate 1.1.1 / torch 2.5.1:
#   - diffusers==0.37.1: first release line that exports Flux2KleinPipeline
#     (FLUX.2 klein), ZImagePipeline (Z-Image-Turbo) and QwenImagePipeline
#     alongside the pipelines this sidecar already used. Verified against the
#     tagged source: diffusers/__init__.py at v0.37.1 exports Flux2KleinPipeline,
#     ZImagePipeline, QwenImagePipeline, WanPipeline, AutoencoderKLWan,
#     BitsAndBytesConfig and PipelineQuantizationConfig. 0.37.1 declares
#     huggingface-hub>=0.34,<2.0 and safetensors>=0.3.1. (0.38+ raises the
#     safetensors floor to a release candidate and 0.40+ needs huggingface-hub
#     1.x and torch>=2.6, so 0.37.1 is the deliberate stopping point.)
#   - transformers==4.57.3: the last 4.x line (needs huggingface-hub<1.0). It
#     provides the Qwen3 (FLUX.2 klein, Z-Image text encoders) and
#     Qwen2.5-VL (Qwen-Image text encoder) model classes the new pipelines
#     load, and still has the tokenizer-loading behavior the pins below were
#     validated against. transformers 5.x is not used: it is a major version
#     with a different tokenizer stack.
#   - bitsandbytes==0.48.2: nf4 / 8-bit quantized loads (requires torch>=2.3).
#   - The base image moves to torch 2.7.1 / CUDA 12.6 (see the Dockerfile).
diffusers==0.37.1

# Full text-encoder tokenizer stack (citadel-cli#829). AutoTokenizer /
# AutoPipelineForText2Image / WanPipeline silently depend on different
# optional backends per model family, and a missing one fails at model-LOAD
# time (mid-provision, on the node), not at image-build time. sentencepiece +
# protobuf back the T5 tokenizer used by SD 3.5 Medium and LTX-Video, and the
# UMT5 tokenizer citadel #958's Wan2.1 text-to-video model
# (Wan-AI/Wan2.1-T2V-1.3B-Diffusers, DIFFUSERS_VIDEO_MODEL's default) uses --
# same sentencepiece-backed T5 family; ftfy is CLIPTokenizer's optional
# text-cleaning backend (used by the default SDXL-Turbo). Real incident:
# LTX-Video's T5 tokenizer failed twice in a row
# on a live node -- first `ModuleNotFoundError: No module named 'tiktoken'`
# (this transformers version's tokenizer-loading path imported it on that
# model's tokenizer even though tiktoken's own BPE format isn't otherwise
# involved -- root cause not fully traced beyond the observed error; treat as
# an empirical requirement for this pin set, not a documented mechanism), then
# `ValueError: Error parsing tokenizer/spiece.model` once tiktoken alone was
# hand-installed but sentencepiece/protobuf were not (reproduced locally:
# services/diffusers-service/scripts/check_tokenizer_deps.py fails the same
# way against Lightricks/LTX-Video's tokenizer with sentencepiece
# uninstalled). Bake all four so no supported model can hit this class of
# failure again. Pinned to versions contemporaneous with the
# transformers/diffusers pins above; do NOT loosen any pin in this file when
# adding to it.
sentencepiece==0.2.1
protobuf==5.28.3
tiktoken==0.12.0
ftfy==6.3.1
fastapi==0.115.6
uvicorn==0.34.0
pydantic==2.10.4
